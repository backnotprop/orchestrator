# Batch Launch CLI

Date: 2026-06-22

## Status

Draft spec.

## Intent

Let agents start several child agents with one CLI call, then manage the whole
set using the same compact JSON control flow that already exists for read,
watch, ps, and interrupt.

This fixes the main remaining agent-CLI inefficiency: launching many agents
currently means calling `orchestrator launch` many times.

## CLI Shape

Add file/stdin mode to `launch`:

```sh
orchestrator launch --file agents.json --json --compact --brief
orchestrator launch -f agents.json --json --compact --brief
orchestrator launch -f - --json --compact --brief
```

Keep current single launch unchanged:

```sh
orchestrator launch codex --name "inspect api" --json --compact "Inspect the API."
```

Rules:

- `--file` / `-f` means batch mode.
- Batch mode requires `--json`.
- `--compact` is optional but should be what agents use.
- `--brief` works only with `--compact`, same as single launch.
- Batch mode cannot also pass a positional runtime or positional task.
- Batch mode starts tasks in the background by default.
- Batch `--wait` is not part of the first slice. Use returned
  `commands.waitPreview.args`.

## Manifest Shape

Use JSON:

```json
{
  "schemaVersion": 1,
  "defaults": {
    "runtime": "codex",
    "model": "gpt-5.4-mini",
    "cwd": ".",
    "timeoutMs": 300000,
    "maxOutputBytes": 2000000
  },
  "tasks": [
    {
      "name": "inspect cli",
      "task": "Inspect the CLI package."
    },
    {
      "runtime": "claude-code",
      "model": "haiku",
      "name": "review docs",
      "task": "Review the docs."
    }
  ]
}
```

Task fields:

- `runtime`
- `task`
- `name`
- `cwd`
- `model`
- `outputMode`
- `timeoutMs`
- `maxOutputBytes`

`runtime` may come from `defaults`. `task` must be present per item. `name` is
strongly recommended.

CLI options still provide outer context:

- `--workspace`
- `--orchestrator-dir`
- `--config`
- `--allow-disabled-runtime`

Precedence:

1. per-task manifest field;
2. manifest `defaults`;
3. CLI default flags such as `--cwd`, `--model`, `--output-mode`,
   `--timeout-ms`, and `--max-output-bytes`;
4. runtime defaults.

## Output Shape

Compact batch launch should return one JSON object:

```json
{
  "schemaVersion": 1,
  "summary": {
    "requested": 2,
    "launched": 2,
    "active": 2,
    "failed": 0
  },
  "commands": {
    "readPreview": {
      "args": ["read", "abc12345", "def67890", "--max-bytes", "16000", "--json", "--compact"]
    },
    "waitPreview": {
      "args": [
        "read",
        "abc12345",
        "def67890",
        "--wait",
        "--timeout-ms",
        "300000",
        "--max-bytes",
        "16000",
        "--json",
        "--compact"
      ]
    }
  },
  "stop": {
    "kind": "tasks",
    "ids": ["abc12345", "def67890"],
    "args": ["interrupt", "abc12345", "def67890", "--json", "--compact"]
  },
  "tasks": [
    {
      "index": 0,
      "id": "abc12345",
      "taskId": "abc12345-full",
      "name": "inspect cli",
      "runtime": "codex",
      "model": "gpt-5.4-mini",
      "status": "running",
      "active": true
    },
    {
      "index": 1,
      "id": "def67890",
      "taskId": "def67890-full",
      "name": "review docs",
      "runtime": "claude-code",
      "model": "haiku",
      "status": "running",
      "active": true
    }
  ]
}
```

Non-compact `--json` may include full per-task command bundles and paths if we
want parity with single launch. For agent use, compact is the important path.

`--brief` should omit per-task `commands` and keep top-level `commands` and
`stop`.

## Error Behavior

Preflight validation must be all-or-none.

Before launching anything:

- parse the manifest;
- validate schema;
- validate every task item;
- merge defaults;
- build every launch plan;
- validate each normalized launch request before starting any task.

If preflight fails, print machine-readable JSON when `--json` is set:

```json
{
  "schemaVersion": 1,
  "error": {
    "name": "CliError",
    "reason": "invalid_launch_manifest",
    "input": "tasks[1].runtime",
    "message": "tasks[1].runtime is required because no default runtime is set."
  }
}
```

No task files should be created on preflight failure.

If a launched runtime later fails, that is a normal task failure. It should be
visible through `read`, `events`, `logs`, and `ps`.

## Implementation Plan

1. Add launch manifest types in a CLI module, for example:

   ```text
   packages/cli/src/launch-manifest.ts
   ```

2. Add a normalized internal launch request type:

   ```ts
   type NormalizedLaunchRequest = {
     runtime: string;
     task: string;
     cwd: string;
     name?: string;
     model?: string;
     outputMode?: string;
     timeoutMs?: number;
     maxOutputBytes?: number;
   };
   ```

3. Extract the current single-launch preparation into a reusable helper:

   ```ts
   buildCliLaunchTaskInput(request, context, registry): LaunchTaskInput
   ```

   The helper should own:
   - `buildAgentLaunchPlan`;
   - runtime default timeout/output cap;
   - task id allocation;
   - model/name propagation;
   - workspace/cwd/label propagation.

4. Keep one launch execution helper:

   ```ts
   launchCliTask(input, { wait }): Promise<AgentTaskRecord>
   ```

   Single launch and batch launch both use it.

5. Add batch launch handling inside `commandLaunch`:
   - if `options.file` is absent, run existing single path;
   - if `options.file` is present, read/parse/preflight all requests;
   - launch all tasks after preflight passes;
   - return batch JSON.

6. Build batch JSON using existing helpers:
   - `taskCommandSummary` for task rows;
   - `taskBatchControlCommands` for top-level read/wait commands;
   - the same `stopArgsSuffix(...)` logic used by current compact payloads.

7. Update `help --json --compact`, `SKILL.md`, and README examples after the
   command exists.

## Test Plan

Add focused tests, probably in `test/cli-launch.test.ts` or a new
`test/cli-batch-launch.test.ts`.

Cover:

- `launch -f file --json --compact --brief` launches multiple tasks;
- `launch -f - --json --compact --brief` reads stdin;
- manifest defaults apply;
- per-task fields override defaults;
- top-level `commands.waitPreview.args` works;
- top-level `stop.args` interrupts only launched active tasks;
- invalid JSON returns machine-readable error;
- missing `tasks` returns machine-readable error;
- missing runtime with no default returns machine-readable error;
- bad runtime in one item launches nothing;
- `--file` with positional runtime/task is rejected;
- `--brief` keeps top-level commands but omits per-task commands.

## Non-Goals

- No YAML in the first slice.
- No JSONL in the first slice.
- No declarative `apply`.
- No persistent batch object.
- No new task group table.
- No batch restart/resume.
- No special provider behavior.

Batch launch is just a better way to start several normal tasks.
