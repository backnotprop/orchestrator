# Research Spike: Resume Pi Sessions

Date: 2026-06-29

Sub-agent: Euclid

## Question

Can Orchestrator programmatically resume a prior Pi-backed parent-agent session
or a Pi child runtime session?

## Short Answer

Parent-agent sessions: yes at the Pi SDK level, but not through current
`orchestrator run` CLI or task records. Orchestrator can resume by passing a Pi
`SessionManager.open(...)` or `SessionManager.continueRecent(...)` into
`createOrchestratorParentSession`.

Pi child runtime sessions: not with the current task launch path. The `pi`
runtime declares resume support, but Orchestrator's launch-plan builder does
not use it, and the process executor runs Pi as a one-shot `pi -p` process.

## Resume Model

Pi's durable resume handle should be the session file path. The session ID is
useful, but it is scoped by session directory and cwd conventions, so exact
path is less ambiguous.

For parent-agent resume, Orchestrator would resolve `agentDir`, `sessionDir`,
and cwd, open or continue a Pi `SessionManager`, pass it into
`createOrchestratorParentSession`, then prompt the resumed session. Pi would
restore messages, model, provider, and thinking state.

For Pi child runtime resume, Orchestrator would need either a one-shot resume
launch such as `pi --session <path> -p <prompt>` or a real Pi RPC executor that
keeps stdin open, sends JSON commands, and tracks `sessionFile`/`sessionId`.

## What Orchestrator Would Store

- Parent session ID.
- Exact parent session file path.
- Parent `agentDir`, `sessionDir`, cwd, and workspace root.
- Parent run/task IDs that created or resumed the session.
- Optional restored provider/model metadata for display and diagnostics.
- For Pi child tasks, exact Pi session file plus session ID.

## Risks

- Session IDs alone are ambiguous across agent dirs, session dirs, and
  workspaces.
- Existing foreground `orchestrator run` emits only `sessionId`; recovery
  requires scanning session directories.
- Failed early sessions may have an ID before a durable file is useful.
- Resuming a parent session can expose stale tool results or old child-task
  context.
- Pi model restore depends on provider/model config and auth still working.
- The current `pi` runtime resume setting is declarative only.
- Mixing `~/.pi/agent` and `~/.orchestrator` sessions could confuse operator,
  parent, and child history.

## Recommendation

Implement parent-agent resume first. Add explicit
`orchestrator run --session <path|id>` and `orchestrator run --continue`, backed
by Pi `SessionManager.open` and `continueRecent`. Emit and store `sessionFile`
alongside `sessionId` for foreground JSON, stream events, and background parent
task records.

Defer generic Pi child-runtime resume until there is a concrete workflow. When
added, make it explicit to the Pi runtime and store the exact child session
file.

Do not build a universal resume engine yet. The smaller launch-shaped version
is parent session resume plus exact session-file persistence.

## Unknowns

- Whether the installed `pi` binary exactly matches this local source.
- Whether Pi should expose a stable session lookup API by ID.
- Best schema location for `parentSessionFile`.
- Whether foreground `orchestrator run` should create a task record once
  session resume becomes a core feature.
